# Razorpay Capability Matrix
Verified: Aug 28, 2026 (against live Razorpay docs)

| API | Confirmed capability | Doc reference | Gotchas |
|---|---|---|---|
| **Orders API** | Dynamic `amount` at creation — **YES** | [Create an Order](https://razorpay.com/docs/api/orders/create/) | Amount must be passed in the smallest currency subunit (e.g. paise for INR: ₹299 → `29900`). The order amount is fixed once the order is created — the checkout flow signs `razorpay_order_id` + `razorpay_payment_id` together, so a payment can't be completed against a tampered amount. |
| **Orders API** | Native idempotency key support — **NO** | [Idempotency Overview](https://razorpay.com/docs/api/x/payout-idempotency/) | Header-based idempotency (`X-Payout-Idempotency`) is only supported on **Payouts** and **Refunds** APIs, not Orders. For Orders, dedupe must be enforced via the unique `receipt` field and/or our own application logic keyed on `deals.session_id`. |
| **Payment Links API** | Dynamic amount per link — **NO** | [Payment Links FAQs](https://razorpay.com/docs/payments/payment-links/faqs/) | Payment Links are fixed-amount only — the customer cannot enter their own amount. `accept_partial` only allows splitting one fixed amount into installments, not variable pricing. **Implication: we must create a new Payment Link per negotiated deal, not reuse one link across sessions.** |
| **Webhooks** | Exact event names for payment success | [Webhooks](https://razorpay.com/docs/webhooks/validate-test/) | `payment.captured` — funds actually settled. `order.paid` — order-level confirmation, useful when tying settlement directly to our Orders-based flow. Note: `payment.authorized` fires first and only means funds are *locked*, not settled — do not treat `authorized` as deal-closed. |
| **Webhooks** | Signature verification method | [Validate and Test Webhooks](https://razorpay.com/docs/webhooks/validate-test/) | HMAC-SHA256 over the **raw, unparsed request body**, keyed with the webhook secret, sent in the `X-Razorpay-Signature` header. **Critical for our Express setup:** must NOT apply `express.json()` globally before this route — use `express.raw()` on the webhook route specifically (or capture raw body via a verify callback), or the recomputed hash will never match. |
| **Webhooks** | Delivery guarantees | [Webhooks](https://razorpay.com/docs/webhooks/validate-test/) | At-least-once delivery — the same event can be received more than once. Events can also arrive **out of order** (e.g. `payment.authorized` after `payment.captured`). Use the `X-Razorpay-Event-Id` header to dedupe. Our webhook handler must be idempotent and tolerant of out-of-order events, not just tolerant of retries. |
| **Test mode** | Key generation, KYC friction — **ZERO FRICTION** | [API Keys Generator](https://razorpay.com/docs/payments/dashboard/account-settings/api-keys/) | Test Mode API keys can be generated instantly, with no website details and no KYC required. Live Mode requires website verification (up to 3 working days) and completed business KYC. |

## Direct implications for our architecture

1. **Settlement path = Orders API, not Payment Links, for the core flow.** Payment Links' fixed-amount constraint conflicts with our dynamically-negotiated amount unless we create one Payment Link per deal (fine for the demo, since each deal is a one-off anyway) — but the Orders API is the more natural fit since we already create a fresh order per negotiated session.
2. **Idempotency is our responsibility, not Razorpay's**, for Orders. `deals.session_id` (UNIQUE constraint, already in our schema) is what prevents a retried settlement call from creating a duplicate order.
3. **Webhook receiver must be built with two properties from day one, not added later:** (a) raw-body signature verification, (b) idempotent handling keyed on `X-Razorpay-Event-Id` or our own `deals.status`, since Razorpay can and will redeliver and reorder events.
4. **No blockers to our plan.** Everything the architecture assumes (dynamic amount, safe custom idempotency, test-mode settlement, webhook confirmation) is achievable — no open questions remain.
